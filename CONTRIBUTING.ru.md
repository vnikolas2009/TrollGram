# Как внести вклад в TrollGram

Спасибо за интерес к проекту. TrollGram --- это набор собственных
изменений поверх большой кодовой базы iOS-клиента, поэтому небольшие и
хорошо описанные pull request обычно проще проверить, чем масштабные
переделки.

Ниже описан рекомендуемый порядок работы. Если какое-то правило не
подходит к вашей задаче, объясните причину в pull request.

## Перед началом

1.  Прочитайте [README](../README.md), чтобы понять назначение проекта и
    его ограничения.
2.  Проверьте [существующие
    issues](https://github.com/vnikolas2009/TrollGram/issues), прежде
    чем создавать повторный отчёт или начинать исправление.
3.  Если изменение крупное, сначала откройте issue и опишите проблему и
    предполагаемое решение. Так меньше риск потратить время на функцию,
    которая не подходит проекту.
4.  Не начинайте работу со старого форка, пока не проверите, насколько
    он отстаёт от основной ветки.

Для небольших исправлений документации и очевидных багфиксов
предварительное обсуждение не требуется.

## Какие изменения полезны

Например:

-   Исправления ошибок, которые можно воспроизвести.
-   Улучшения настроек приватности и их связи с рантаймом.
-   Исправления хоста Python-плагинов и слоя совместимости.
-   Документация, переводы и инструкции по сборке.
-   Тесты и диагностика, помогающие находить регрессии.
-   Улучшения GitHub Actions, которые не раскрывают секреты и не
    ослабляют безопасность репозитория.

Не стоит отправлять массовое форматирование несвязанных upstream-файлов.
Старайтесь делать diff настолько небольшим, насколько позволяет задача.

## Подготовка окружения

Используйте версии инструментов из [`versions.json`](../versions.json).
Для сборки нужны macOS, Xcode, Python и Bazel.

``` bash
git clone --recursive https://github.com/vnikolas2009/TrollGram.git
cd TrollGram
python3 build-system/setup_python.py
```

Если подмодули не загрузились:

``` bash
git submodule update --init --recursive
```

Актуальная команда сборки неподписанного IPA приведена в
[README](../README.md). Успешная компиляция полезна, но сама по себе не
заменяет проверку поведения приложения на устройстве.

## Ветки и коммиты

-   Создавайте отдельную ветку для каждого изменения.
-   Один pull request --- одна задача или несколько тесно связанных
    изменений.
-   Пишите понятные сообщения коммитов, например:
    -   `Fix plugin import error handling`
    -   `Document privacy flag behaviour`
    -   `Prevent duplicate message archive entries`
-   Не добавляйте в Git результаты сборки, локальные кэши, сертификаты,
    provisioning profiles, IPA, личные логи и секреты.
-   Не форматируйте большие upstream-файлы без необходимости.

## Требования к коду

### Swift

-   Следуйте стилю окружающего файла.
-   Предпочитайте минимальное безопасное изменение полной переработке.
-   Делайте состояние приватности и сетевое поведение явными.
-   Не добавляйте новые зависимости без необходимости; проверяйте
    совместимость их лицензий.
-   Не меняйте незаметно значения настроек по умолчанию и форматы
    пользовательских данных.

### Python-плагины

-   Делайте слой совместимости предсказуемым и документируйте
    неподдерживаемые API.
-   Ошибки в файле плагина и исключения Python не должны приводить к
    падению всего приложения.
-   Не предполагайте, что Android API exteraGram существуют на iOS.
-   Не добавляйте сетевые запросы и операции с файлами без необходимости
    и описания.
-   Не включайте плагины, собирающие пароли, файлы сессий или личные
    сообщения.

### Приватность и сообщения

Изменения, затрагивающие уведомления о прочтении, статус присутствия,
архив сообщений, защищённый контент или одноразовые медиа, требуют
особенно внимательной проверки.

В pull request для таких изменений укажите:

1.  Какой запрос Telegram, событие или локальное поведение
    затрагивается.
2.  Какие типы чатов и сообщений проверялись.
3.  Что не меняется или пока не поддерживается.
4.  Может ли изменение приводить к локальному сохранению сообщений или
    метаданных.
5.  Какие ограничения связаны с серверной обработкой или другими
    клиентами.

Не описывайте клиентское изменение как абсолютную гарантию приватности.

## Проверка изменений

Единой команды, которая проверяет все функции форка, нет. По
возможности:

-   Соберите затронутую цель или всё приложение.
-   Проверьте поведение на реальном устройстве либо укажите конфигурацию
    симулятора.
-   Для изменений плагинов проверьте корректный файл, некорректный файл
    и плагин, который вызывает исключение.
-   Для архива проверьте повторные события, редактирование и удаление
    сообщений.
-   Для настроек проверьте включение, отключение и повторный запуск
    приложения.
-   Укажите точные версии Xcode и iOS, модель устройства и конфигурацию
    сборки.

Если полную сборку выполнить не удалось, напишите об этом прямо. Не
выдавайте непроверенное изменение за протестированное.

## Чек-лист перед pull request

-   [ ] Изменение решает конкретную проблему.
-   [ ] В diff нет лишних сгенерированных файлов и массового
    форматирования.
-   [ ] В репозиторий не попали секреты, данные аккаунта или личная
    информация.
-   [ ] Документация обновлена, если изменилось поведение или процесс
    настройки.
-   [ ] Выполнены относящиеся к изменению тесты или ручные проверки.
-   [ ] Ограничения и непроверенные случаи перечислены честно.
-   [ ] Авторские уведомления и лицензии upstream- и сторонних
    компонентов сохранены.

Хорошее описание pull request содержит разделы **Контекст**, **Что
изменено**, **Как проверено** и **Известные ограничения**.

## Сообщения об ошибках

Создавая issue, укажите:

-   Краткий и конкретный заголовок.
-   Ожидаемое и фактическое поведение.
-   Шаги для повторения ошибки.
-   Модель устройства и версию iOS.
-   Версию TrollGram или hash коммита.
-   Версию Xcode и конфигурацию сборки, если проблема связана со
    сборкой.
-   Фрагмент лога или скриншот без личных данных.

Сначала убедитесь, что похожего issue ещё нет. Не прикладывайте сессии
аккаунта, API hash, номера телефонов, личные переписки и полные архивы
приложения.

## Сообщения об уязвимостях

Не публикуйте рабочий эксплойт и чувствительные подробности уязвимости в
открытом issue. Свяжитесь с сопровождающим через приватный способ связи,
опубликованный владельцем репозитория. Приложите достаточно информации
для безопасного воспроизведения проблемы.

## Проверка pull request

Pull request может потребовать доработки, задержаться или быть закрыт,
если изменение не относится к проекту, не воспроизводится, без
необходимости меняет upstream-код или не содержит информации для
проверки. Сам факт открытия pull request не означает, что он будет
принят.

Спасибо за помощь в развитии TrollGram.
